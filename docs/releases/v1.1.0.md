# Idryx 1.1.0

An event is ingested into the identity graph as the source it claims only when the file it was read from may carry that source.

## What 1.1 changes, and what it leaves frozen

`compat/1.0.json` is unchanged in its `frozen` lists: no subcommand, exit code,
route, frozen environment name, emitted or consumed event type or format moved,
and `scripts/compat-surface.sh` holds that. One optional environment name,
`IDRYX_STREAMS`, is new, and the manifest records it under `additive`, the
category for a name that only widens what a bus file may carry. That is why
this is a minor release and not a patch: a new variable and a new refusal, both
inside the 1.x promise.

## Since 1.0.0

- **A line in the wrong file is not ingested** (#91, bus layer 2, the reader
  half). Idryx used to verify a bus file's `prev_hash` chain and then ingest
  every well-formed line as the source it claimed, and the chain is unkeyed, so
  a line claiming `source: wardryx` inside `tokenfuse.ndjson` put a wardryx
  identity and event into the graph. Now `<source>.ndjson` carries `<source>`
  for the fourteen registered sources, `tokenfuse-cloud.ndjson` and
  `tokenfuse-mcp.ndjson` carry `tokenfuse`, and `IDRYX_STREAMS` declares
  anything else. A refused line creates neither identity nor event, is counted
  as `Report.ForeignSource` beside the malformed lines, and its (file, claim)
  pair is named on stderr, one escaped, bounded line each, never fatally. A glob
  is judged file by file. The chain is still verified over the whole file as
  written, before any line is refused.
- **A stream nobody declared is ingested and named.** A file whose lines claim
  its own name is still read (a plane new to the box must not go unseen) and is
  named on stderr as unknown; a line in it claiming any other source is refused.
- **`IDRYX_STREAMS`**: `stem=source|source`, comma-separated, read by every
  subcommand that loads a bus source (`detect`, `serve`, `bom`, `ai-inventory`,
  `remediate`, `load`). It widens and never narrows. A malformed entry refuses
  the load naming the variable.
- **`demo.ndjson` is opt-in**, not built in: any co-tenant of the events
  directory could create it and speak as six planes. Declare it with
  `IDRYX_STREAMS=demo=tokenfuse|wardryx|engram|qryx|verdryx|mockryx`.
- **The test fixtures and README examples are named for the source they
  carry** (`testdata/tokenfuse.ndjson`, `testdata/<source>/<source>.ndjson`),
  because the old generic names are exactly the shape the rule refuses.
- **First `features/` directory** and `scripts/features-are-bound.sh`: twelve
  scenarios, each bound to a named test both ways, run in CI's `build` job and
  covered by four cases in `scripts/gates-have-teeth.sh`.
- **Shared contract dependency** (#86, #87): agent-stack-go v1.0.0 to v1.0.2.
  v1.0.1 bounds an RSA modulus inside delegation's key parsing, a path this
  repository does not reach; the event and passport packages Idryx imports are
  unchanged.
- **CI and release actions** (#85, #88, #90): `docker/setup-qemu-action`
  4.4.0, `docker/setup-buildx-action` 4.4.1 and `docker/build-push-action`
  7.4.0 in `release.yml`, `actions/upload-artifact` 7.0.1 and
  `github/codeql-action/upload-sarif` 4.38.2 in the Scorecard workflow, each
  still pinned to a commit.
- **The eBPF sensor's x86_64 build has now been run** (#89, documentation):
  `ebpf-capture` from the v1.0.0 image captured 349 flows in 70 seconds on an
  x86_64 BTF kernel on 2026-09-27, and a real governed agent's own flows carried
  its claimed identity. The record is in `SECURITY.md`.

## Upgrade note, 1.0.0 to 1.1.0

- A bus file whose name stem differs from the `source` its lines claim is now
  refused, and stderr says so. This reaches any invocation that loads a bus
  source, for example `--load tokenfuse:<path-or-glob>` or `--source tokenfuse`.
  Either rename the file for its source (`wardryx.ndjson`) or declare it:
  `IDRYX_STREAMS=events=tokenfuse|wardryx`. A descriptor that named a generically
  named file (`events.ndjson` carrying several planes) must be declared.
- `demo.ndjson` is no longer read as six planes. Set the `IDRYX_STREAMS`
  declaration above if you load a demo file. `taipan up` starts idryx with an
  empty environment and `--load tokenfuse:<its own file>`, so nothing in the
  estate's launchers reads `demo.ndjson` today.
- Nothing is removed or renamed. The Postgres schema, the `identity_finding`
  event and its schema versions, the detectors and the CycloneDX output are as
  in 1.0.0, and a refused line is never persisted anywhere. The release asset
  names still carry no version.
- A box that already names its files for their source needs no change.

## Evidence and limit

373 test functions (338 at 1.0.0); twelve scenarios in
`features/source-must-match-its-stream.feature`, 12 bindings, 0 broken. #91's
behavioural tests were run against the unfixed tree first (eight red on
behaviour, two guard against over-refusing and are held by mutants), and eight
mutants of the fix were each caught by a named test. The real binary,
`bom --format json --load "tokenfuse:<dir>/*.ndjson"`, listed six agents before
the change with the forged one among them, and three after.

## Not proven

- A live box with a hostile co-tenant: the run used a directory written by hand.
- `idryx load` (the Postgres path) reaches the same door and has no integration
  test for the rule.
- A process that creates `wardryx.ndjson` before wardryx does and writes
  `source: wardryx` into it passes, because the name and the claim agree.
  Directory ownership in the launchers and a per-file owner-uid check would
  close that, and neither is built.
- A writer compromised in its own uid can still forge its own stream; only
  signing closes that.
- The exception table is a copy that Idryx and heraldyx each carry; nothing
  holds the two equal.
- The table's file names are a reading of the producers' and launchers' code,
  not a run on a deployed estate. verdryx, engram and qryx have no
  launcher-configured file; their names are the convention.
- The eBPF sensor has still not run on a real fleet or a cloud host, and the
  `object-matches-its-source` gate and the four BPF teeth cases run only in the
  Linux `ebpf` job, not on the machine that prepared these notes.
