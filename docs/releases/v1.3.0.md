# Idryx 1.3.0

A minor release on the 1.2 surface. The `detect` webhook can take its headers from a file, so a credential no longer has to be typed on the command line, where other users can read it in the process list. The change is additive: no existing flag, environment name, frozen name or exit code changes meaning.

## Upgrade

Nothing breaks, and an existing run needs no edit. One thing is new on stderr: a `--webhook-header` whose name looks like a credential (`Authorization`, `Cookie`, or any name containing `key`, `token` or `secret`, in any letter case) is still sent, and idryx prints one line that names the header and never its value.

To keep a webhook credential off the command line:

1. Write the header lines to a file, one `Name: Value` per line. Blank lines and lines that start with `#` are skipped.
2. Make the file a regular file, owned by the account that runs idryx, with mode `0600`: `chmod 600 <file>`.
3. Pass the path with `--webhook-header-file <path>`, or set `IDRYX_WEBHOOK_HEADER_FILE` to it. The flag wins when both are set. Both are read only when `--webhook` is set.

The owner rule, in full. A file owned by the running account is accepted at `0600` or stricter. A file owned by root is accepted at `0640` or stricter, which is the shape a Kubernetes Secret mounted with an `fsGroup` presents to a non-root process. A file owned by any other account is refused, and so is any file with a bit for other users, or a group write or execute bit. A symbolic link is judged by its target. Run idryx as the non-root account the image sets: a root process compares the owner with itself first, so a root-owned file must then be `0600`.

A refusal names the file and its mode and never prints a header value. A malformed line is refused by its line number, without echoing the line.

Windows: the owner and mode check is not made, because Go reports a writable file on Windows as 0666 whatever its ACL says. The regular-file rule still applies. On Windows, protect the header file with its ACL instead.

## What changed since 1.2.2

- **Webhook headers from a file.** `--webhook-header-file <path>` and `IDRYX_WEBHOOK_HEADER_FILE` read the webhook's headers from a file, under the owner rule above. A command-line header with the same name as a file header overrides it. The header file rule is the first release of this flag, so there is no earlier rule to migrate from.
- **Credential-looking command-line headers are named on stderr.** A `--webhook-header` with a credential-looking name is sent as before, with one stderr line that names the header. Its value is not printed.
- **agent-stack-go v2.0.1.** A dependency bump (#110). Nothing in idryx's own surface moves with it.
- **v1.2.2 upgrade section (#111).** A documentation commit after the 1.2.2 tag. It describes the event stream file mode that 1.2.2 already shipped. No code change.

## Evidence and limit

- 403 test functions (README badge 403). 31 scenarios across the `features/` directory, each bound to a named test, 0 broken. The owner rule is tested with an injected file mode and owner, so those cases run without privilege.
- Gates run on the release commit are listed in the release PR description.

## Not proven

- A Kubernetes Secret mount on a cluster: not run. The root-owned case is tested with an injected owner, not by a root process.
- Windows: the owner and mode check is not made, and the Windows branch is tested with an injected operating system, not on a Windows host.
- No live run against a real webhook endpoint in this release.
- The credential warning matches on the name, so a harmless name that contains `key` also gets the line. It is a warning, not a refusal.
